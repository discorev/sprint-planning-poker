Scope boundary

Frontend replacement only.

The node-server and sam-server implementations remain protocol-compatible and unchanged. React must meet the existing servers where they are; changing the wire format would turn a contained migration into a cross-stack project.

A

Judgment calls first

Decisions worth changing now

These choices shape the migration. Each has a recommended pick and a real alternative rather than burying product and engineering decisions inside implementation detail.

DECISION 01 · WEAKEST POINT

Deployment-free E2E is the parity contract

Skaffold cannot currently build the legacy frontend, but the live deployment at ollies.dev/sprint-planning-poker/ remains available as a visual and interaction reference. Automated parity checks must still require no deployment.

Confirmed directionCapture a small set of reference states from the live app during implementation, then have Playwright start the real node-server and local Vite preview through its webServer configuration. CI and local E2E remain fully self-contained.
Maintenance boundaryThe live deployment is an acceptance oracle, not a test dependency. Keep a compact behavioral suite—not a hosted-environment check or brittle screenshot matrix—with one complete round plus focused observer, rejected-registration, and reconnect scenarios.
DECISION 02 · STATE

A reducer, not a state library

The application has one shared player list and a handful of round fields. Even a burst of WebSocket activity for 6–7 players changes only a tiny in-memory array and a small DOM; the risk comes from careless reference churn, not message volume at this scale.

Plan’s pickUse a typed useReducer at the app boundary with structural sharing: preserve unchanged player objects, replace only changed players, memoize PlayerCard, and pass stable callbacks. Messages remain ordered and immediate; no throttling or lossy coalescing.
Scale triggerIntroduce an external store only if the product grows into large rooms or several independently updating screens. Zustand would then provide selector-based subscriptions without changing the wire protocol.
DECISION 03 · WEBSOCKET

Native WebSocket state machine

RxJS currently wraps one connection and several Subjects. React does not need that dependency to preserve retry, registration confirmation, message forwarding, and reconnect registration.

Plan’s pickA small typed PlanningPokerSocket class plus usePlanningPokerSocket hook. Reconnect after one second, retain the registered name, and re-register on open exactly as today.
Lowest-diff alternativeKeep RxJS and port the services almost line-for-line. This reduces conceptual change but retains an otherwise unnecessary runtime dependency and service pattern.
DECISION 04 · STYLING

Retire Bootstrap 4 and jQuery

The current Bootstrap grid and modal are the main source of legacy frontend coupling. Keeping them would leave the React app dependent on global scripts and imperative DOM calls.

Confirmed directionRecreate the current appearance with Tailwind utilities and a small theme-token layer—no CSS Modules or bespoke component stylesheets. Retain FontAwesome Pro and standardize its credential on FONTAWESOME_PACKAGE_TOKEN across local builds, Docker, Skaffold, and CI.
Styling boundaryUse arbitrary Tailwind values only where the existing UI requires them, such as the 2.5:3.5 card ratio. Do not introduce a parallel custom-CSS component system or carry Bootstrap into the React app.
DECISION 05 · CUTOVER

Replace frontend/ in place

The app is too small to justify a strangler setup, and dead Angular code must not remain on the live branch.

Confirmed directionOn the migration branch, replace the contents of frontend/ atomically with the React app. Reviewable commits may stage protocol, UI, tests, and deployment, but every commit intended for the live branch contains one frontend implementation—not Angular and React side by side.
Rollback mechanismRollback is Git history or the previous container image, not a second source tree. No react-frontend/, compatibility shell, or retained Angular build enters main.
DECISION 06 · TOOLCHAIN

Vite + React + TypeScript + Bun

There is no SSR, routing, or framework-specific backend integration. A meta-framework would be unnecessary. The frontend’s current npm lockfile can be replaced as part of the toolchain reset.

Plan’s pickUse current stable React, Vite, Tailwind, strict TypeScript, Bun, Vitest, Testing Library, and Playwright. Pin the runtime version in CI and Docker rather than inheriting Node 16.
Conservative alternativeUse pnpm with Node LTS if keeping the entire repository on one JavaScript runtime/package-manager family matters more than frontend build speed.
!

The protocol parser must preserve independent branch order.

Server messages are structurally distinguished and may contain overlapping fields. The current handler applies name/selected, then players, then snooze, reset, and choices as separate if blocks. The React implementation should encode and test that exact order rather than “cleaning it up” into mutually exclusive cases.

Risks and containment

Where parity could quietly slip

H

Overlapping protocol fields

Contain with a pure, order-preserving message reducer and fixtures copied from both frontend tests and Node server broadcasts.

H

Reconnect identity

Contain with fake-timer unit tests plus a browser test that terminates the connection, waits for retry, and verifies automatic registration.

M

Subpath deployment

Contain by testing built assets and WebSocket URLs under /sprint-planning-poker/, not only Vite’s root development URL.

M

Visual drift after Bootstrap removal

Contain with a short set of baseline screenshots at desktop and mobile widths, while allowing accessibility-preserving semantic markup changes.

L

E2E maintenance cost

Contain by testing a few durable user journeys through roles and visible outcomes, not implementation details or full-page pixel snapshots. Run locally and in CI with Playwright-managed processes, never a deployment.

L

Confetti API typing

Use the library’s typed default API and isolate it behind a tiny celebration function; do not copy the existing @ts-ignore.
