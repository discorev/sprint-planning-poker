Core move

Extract the table before adding another door.

MCP must not pretend to be a WebSocket client. First create a transport-neutral planning-poker session service; then let WebSocket and MCP adapters call the same methods and emit the same state changes.

≡

Hard reveal invariant · no participant sees another vote early.

Before every active voter has chosen, shared state exposes only participant metadata and whether each player has selected. An MCP participant may retrieve its own stored card and rationale because stateless calls cannot rely on durable client-side state; it must never retrieve anyone else’s. On automatic reveal, every client receives the complete choices together. Existing WebSocket behavior remains unchanged apart from the additive server-owned cards field on successful registration.

A

Judgment calls first

Decisions worth changing now

These choices define the product and trust boundary. The mechanics beneath them should be straightforward once the picks are agreed.

DECISION 01 · WEAKEST POINT

One default room, but a real session boundary

The live app has one global collection. MCP tools still need a stable application boundary to act against, but a full multi-room product would inflate this first slice.

Plan’s pickIntroduce a PlanningPokerSession abstraction and expose one configured default session initially. Keep the data structures keyed by session ID so multi-room support is additive rather than another rewrite.
AlternativeImplement multiple user-created rooms immediately. This is cleaner long-term, but it adds room creation, discovery, routing, cleanup, URLs, and frontend ownership to an otherwise backend-focused change.
DECISION 02 · CONFIRMED PROTOCOL FLOOR

MCP 2026-07-28, stateless only

This server deliberately targets the new protocol rather than maximizing compatibility with deployed MCP clients.

Confirmed directionCreate one Node HTTP server, mount Streamable HTTP at /mcp, and implement the 2026-07-28 flow only: server/discover, request-scoped responses, and subscriptions/listen SSE for change notifications—without initialize, Mcp-Session-Id, or protocol-level session state. Older clients fail by design.
Hard exclusionNo version negotiation to 2025-11-25, compatibility adapter, legacy GET SSE endpoint, Last-Event-ID resumption, or hidden stateful mode. Modern POST-based SSE defined by 2026-07-28 is part of the selected transport, not a legacy fallback.
DECISION 03 · REGISTRATION

Agents register exactly like users

The current app is deliberately open: any client that can reach the WebSocket endpoint may claim an available display name and vote. Adding authentication only to MCP would create a second trust model without protecting the existing browser path.

Plan’s pickjoin_session accepts name and observer, applying the same minimum-length and duplicate-name rules as WebSocket registration. Both successful WebSocket registration and MCP join_session return cards, the exact ordered deck owned and accepted by the shared server domain; get_session_state repeats it for stateless recovery. The unique display name remains the public identifier, matching the original server. Only join_session returns a private opaque participantId; later caller operations pass that handle explicitly, while shared state, resources, WebSocket messages, SSE notifications, and other participants’ tool results expose names rather than private handles. No separate bearer token, OAuth, or signing secret; mandatory HTTP Origin validation remains transport security, not user authentication.
Later boundaryAuthentication becomes useful only if the whole app needs identity guarantees—preventing impersonation or unauthorized voting across both WebSocket and MCP clients. That would be a separate product-wide change, not part of agent participation.
DECISION 04 · ROUND CONTEXT

The table should know what it is estimating

A generic agent joining through MCP currently sees players and votes, but no story title or task description. It cannot make an informed estimate without an out-of-band prompt.

Plan’s pickAdd roundId and an optional subject to session state. Require roundId on vote submission so a slow agent cannot vote into a reset round.
AlternativeKeep task context outside the app and require the caller to prompt the agent separately. Smaller backend change, but the MCP server is no longer self-describing or reliable across clients.
DECISION 05 · AGENT LIFECYCLE

Application heartbeat mirrors WebSocket liveness

WebSocket ping/pong detects a dead persistent connection. Stateless MCP has no connection to probe, so it needs the same practical protection at the poker-participant layer instead.

Plan’s pickjoin_session returns the caller’s private participantId, server-selected heartbeat interval, and lease duration. Every successful participant call renews the lease, while a dedicated heartbeat tool keeps an otherwise-idle agent present. leave_session removes immediately; expiry removes crashed or abandoned agents and releases their names and votes.
BoundarySSE comments keep the notification stream and proxies alive; they do not prove that the poker agent is still participating. The application heartbeat remains separate from MCP transport state, and an expired handle must rejoin.
DECISION 06 · EXPLANATIONS

Store rationale beside the estimate

The useful agent contribution is not merely another Fibonacci card—it is a concise reason humans can challenge after reveal.

Plan’s pickAccept an optional rationale with submit_vote, keep it hidden from other participants until reveal, and let the submitting MCP participant recover its own card and rationale through get_session_state. Backend storage lands in this slice; frontend presentation can follow separately.
AlternativeShip numeric voting only. This keeps the first frontend untouched, but provides little advantage over adding another human-shaped socket bot.
!

Current registration resets every vote.

PlayerCollection.push() calls reset(), so an agent joining mid-round currently clears the table. The new domain model must make reset an explicit round transition; joins—especially observers and lease renewals—must never reset implicitly.

Proposed runtime architecture

Solid clay arrows are commands into the domain. Dashed olive arrows are state-change notifications back to adapters. No business rule belongs in either transport layer.

B

Contract design

The agent-facing surface

Agents receive the same player actions as the first-party UI. Tools remain stateless request/response operations; automatic reveal is delivered through the protocol’s modern subscriptions/listen SSE stream.

Discovery guidance and the single participation prompt

McpServer receives server-level instructions, so modern server/discover tells an agent how to participate before it selects a tool. The guidance is concise but covers the complete application lifecycle:

1. join_session once with a unique display name; observers do not vote.
2. Keep participantId private. It is application state, not authentication,
   a bearer token, or MCP transport/session state.
3. Read the round subject, participants, and server-owned cards.
4. Voters submit one advertised card for the current roundId, optionally with
   a concise rationale. On a stale roundId, reread state; do not retry blindly.
5. Use subscriptions/listen for the session resource, then get_session_state
   after each resource update. Use heartbeat while otherwise idle.
6. Never seek another participant’s unrevealed vote. Reveal is automatic when
   all active voters have selected.
7. Reset only after reveal when asked to start another round; snooze by unique
   public name when instructed; leave_session when finished.
1

participate-in-planning-poker is the only prompt.

prompts/list advertises exactly this reusable prompt—no fragmented action prompts. It requires name with a three-character minimum and accepts optional semantic boolean observer (validated from the protocol’s string argument with Zod stringbool). prompts/get returns one concise user-role message customized with the supplied name and voter/observer role, directing the model to use the server tools and resource through the same lifecycle above.

join_session

mutation

Registers the agent under an available public display name, using the same rules as the browser client. Returns the caller’s private application handle, server-selected liveness timings, and the exact ordered card deck accepted by server vote validation.

{
  "input": { "name": "Architecture agent", "observer": false },
  "returns": {
    "participantId": "participant-7f3…",
    "heartbeatIntervalSeconds": 30,
    "leaseDurationSeconds": 90,
    "sessionResource": "planning-poker://sessions/default",
    "cards": ["?", "1", "2", "3", "5", "8", "13", "21"],
    "round": {}
  }
}

get_session_state

read only

Returns the same server-owned cards deck for stateless recovery, participants by unique public name with selected flags before reveal, and the caller’s own stored vote and rationale. No private participant handles are returned. Other participants’ choices appear only after automatic reveal.

{
  "input": { "participantId": "participant-7f3…" },
  "returns": {
    "stateRevision": 18,
    "cards": ["?", "1", "2", "3", "5", "8", "13", "21"],
    "round": { "status": "voting" },
    "participants": [{ "name": "Architecture agent", "selected": true }],
    "ownVote": { "card": "5", "rationale": "Touches storage." }
  }
}

submit_vote

mutation

Records one card and optional rationale for the supplied application participant. Rejects unknown handles, stale round IDs, observers, invalid cards, and post-reveal changes.

{
  "participantId": "participant-7f3…",
  "roundId": "round-12",
  "card": "5",
  "rationale": "Touches storage and reconnect semantics."
}

reset_round

mutation

Starts the next round after the current round has revealed, matching the first-party reset action. Rejects resets while voting is still in progress.

{
  "participantId": "participant-7f3…",
  "subject": "Optional next story"
}

snooze_participant

mutation

Snoozes the caller or another participant when instructed, matching the original WebSocket server’s name-based behavior. The caller uses its private handle; the target uses the unique public display name. A snoozed participant stops counting toward automatic reveal.

{
  "participantId": "participant-7f3…",
  "targetName": "Architecture agent"
}

heartbeat

liveness

Renews an otherwise-idle participant’s application lease. Unknown or expired handles fail and must rejoin; no MCP connection or transport session is created.

{
  "input": { "participantId": "participant-7f3…" },
  "returns": { "alive": true, "leaseDurationSeconds": 90 }
}

leave_session

mutation

Explicitly removes the participant referenced by the application handle and releases its vote. Lease expiry remains the fallback for clients that disappear without calling it.

{
  "input": { "participantId": "participant-7f3…" },
  "returns": { "left": true }
}
→

Reset and snooze are player actions; reveal is an event.

Agents can reset after reveal and snooze themselves or another participant by unique public name, matching first-party capabilities. There is no reveal tool: when all active voters have chosen, WebSockets receive the new state and MCP listeners receive notifications/resources/updated for the session URI, then call get_session_state for their viewer-safe projection.

Stateless registration flow

1 · DiscoverA 2026-07-28 client calls server/discover. No initialize handshake or protocol session is created.
2 · Registerjoin_session supplies a display name and observer flag.
3 · Return contractThe server returns the caller’s private participantId, heartbeat interval, lease duration, and the canonical ordered cards deck. This is the only response that exposes the handle; both transports advertise the same deck.
4 · ListenThe client opens subscriptions/listen for session resource updates over modern request-scoped SSE; notifications carry only the resource URI, never participant handles.
5 · Act explicitlyState, vote, reset, heartbeat, and leave carry the caller’s participantId; snooze additionally targets a player by unique public targetName. No identity is retained by the transport.
↯

Client configuration: HTTP transport, modern protocol era.

Client configuration uses HTTP transport with protocolEra: "modern". Do not select legacy transport type "sse": modern HTTP opens SSE response streams for requests such as subscriptions/listen.

⌁

This intentionally preserves the current trust model.

Any client that can reach the app may claim an unused name and vote. Authentication would prevent impersonation only if it covered browser users too; adding it solely to MCP would add setup and failure modes without securing the table as a whole.

Sequencing

Move the rules, then open the door

The sequence isolates behavior changes before MCP is introduced, so domain regressions are distinguishable from transport and registration bugs.

Freeze current round behavior

Add server-level fixtures and integration tests for register, vote, automatic reveal, reset, observer, snooze, disconnect, and duplicate-name rejection before moving logic out of index.ts.

Gate · existing WebSocket contract covered

Extract the session domain

Introduce private participant handles while retaining names as public identifiers, plus explicit round state, one canonical ordered card deck used by validation and registration responses, caller-aware vote projection, explicit reset, rationale storage, lease pruning, and a single state-change notification.

Gate · domain tests pass without sockets

Rewire WebSocket behavior

Keep existing frontend wire behavior stable while mapping sockets to participant IDs and routing every action through the new domain service. Add the domain-owned cards deck to successful registration and broadcast from one subscription point.

Gate · React client behaves unchanged

Add strict 2026-07-28 modern HTTP

Mount stateless MCP at /mcp with legacy rejection, implement server/discover with server-level participation instructions, expose seven first-party player tools plus the single participate-in-planning-poker prompt, and publish session changes through subscriptions/listen SSE without creating protocol sessions.

Gate · discover succeeds; initialize fails

Match browser registration and liveness semantics

Create application participant handles from open name registration, return the same server-owned cards as browser registration plus server-selected heartbeat timings, renew leases from participant activity, and provide a dedicated heartbeat for agents idle between poker actions.

Gate · liveness cleanup remains application state

Prove modern HTTP/SSE and deliberate legacy failure

Connect with HTTP transport and modern protocol era, open subscriptions/listen, and exercise every player action. Then prove legacy initialize and GET SSE fail while obsolete session and resumption headers are ignored, never created or echoed.

Verification

Tests that prove it is one table

The critical checks cross transport boundaries. An MCP server can pass isolated tool tests while still failing to participate in the browser-visible round.

✓ WebSocket registration contractSuccessful registration preserves existing behavior and advertises the exact ordered domain deck accepted by vote validation.
✓ Caller-aware reveal boundaryBefore reveal, an MCP participant can recover its own card and rationale but never another participant’s; shared and WebSocket state expose selected flags only. Automatic reveal exposes all choices together.
✓ Stale round rejectionAn agent reasoning across a reset receives a typed stale-round error instead of voting into the wrong estimate.
✓ Heartbeat and expiryHeartbeats and poker actions renew the lease; an abandoned participant eventually disappears and releases its name. Before expiry, any player can snooze it out of reveal completion.
✓ Private handle flowOnly join_session returns participantId. Caller actions carry it privately; shared state, resources, WebSocket messages, SSE notifications, and another participant’s tool output expose public names instead.
✓ Cross-transport revealA browser vote completes the round; WebSockets receive the broadcast and MCP listeners receive a resource update before reading the same revealed state.
✓ Server-owned card deckEvery advertised card is accepted by domain validation, MCP join and state recovery advertise the same ordered deck, and React renders server-provided values in order.
✓ Modern protocol boundaryModern HTTP can discover, call tools, and listen; invalid origins or header/body mismatches fail, initialize fails, GET/DELETE return 405, and obsolete headers are ignored.
✓ Agent participation guidanceserver/discover includes the full lifecycle instructions, tool count remains seven, prompts/list exposes exactly one participation prompt, and prompts/get rejects invalid names while customizing voter and observer messages.
✓ Listen reconnectAfter a stream interruption the client resubscribes and reads current state, without relying on unsupported SSE event resumption.
F

Risks and containment

Where the first version can go wrong

M

A live but quiet agent loses its lease

Contain with conservative server-advertised timings, renewal on every player action, a dedicated heartbeat, and fake-clock boundary tests. Stale agents do not block reveal because any first-party player or agent can snooze them.

M

A proxy buffers reveal notifications

Contain with X-Accel-Buffering: no, ingress buffering disabled, SSE keep-alive comments, and a deployed-path test that measures notification delivery rather than only localhost behavior.

H

Implicit resets survive refactor

Contain with tests that join and renew participants during an active round. Only explicit round transitions clear votes.

M

The MCP endpoint is open

This matches the existing WebSocket trust model: reachable clients may claim an unused name and vote. Contain accidental conflicts with duplicate-name checks and document that impersonation prevention requires product-wide authentication later.

M

Current frontend cannot show rationale

Keep backend storage and reveal payload compatible, then choose whether to include the small React presentation slice in the same implementation.

M

A listen stream drops an update

Notifications are invalidation signals, not the source of truth. On connect or reconnect, agents call get_session_state; the server never relies on unsupported Last-Event-ID resumption.

M

Few clients may support the protocol initially

This is an accepted compatibility tradeoff. Document HTTP transport with protocolEra: "modern", test a known 2026-07-28 client, and treat older-client failure as correct behavior.
